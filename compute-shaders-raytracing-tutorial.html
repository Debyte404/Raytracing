The trick is not magic. A pixel becomes a point on the camera plane, the point becomes a direction, and camera position + direction becomes a ray.

Sebastian Lague's ray tracing video works because he starts with a visible question: "How do I draw the same view as the game camera?" He does not begin with a final path tracer. He first draws the camera projection plane, then rays through that plane, then a shader that colors pixels, then sphere hits.

This version follows that same path, but slows down at the places he can move quickly: how the shader gets camera position, what field of view does to directions, why a sphere hit function returns one distance, and how the discriminant tells us the number of intersections.

In Unity, select Main Camera. Turn Gizmos on in Scene View. The visualizer components on the camera are the companion to this tutorial: RayDirectionVisualizer, SphereIntersectionVisualizer, PlaneIntersectionVisualizer, HemisphereBounceVisualizer, and PathTraceStepVisualizer.

The whole story in one sentence

For every pixel, the compute shader creates a world-space ray that starts at the camera, checks what object that ray hits first, and writes the resulting color into a texture.

1. PixelThe GPU worker knows its pixel coordinate, like (x, y) on a canvas.
2. DirectionThe pixel is mapped onto the camera projection plane, then turned into a direction.
3. RayThe direction becomes a ray only after we add the camera position as its origin.
4. HitThe ray asks each object: "do I intersect you, and how far away?"

How does the shader know the camera position?

It does not magically know. This is the part that is easy to miss. A compute shader is just GPU code. It only knows values that Unity/C# gives to it, plus the resources bound to it.

Sebastian's manager script sends camera information to the shader before calling Dispatch. In Unity, the camera component should be found inside a Unity lifecycle method such as OnEnable, not in a field initializer. A field initializer runs before the component instance is ready, which is why private Camera cam = GetComponent<Camera>(); causes compiler error CS0236. 

private Camera cam;

void OnEnable()
{
    cam = GetComponent<Camera>();
    RefreshKernel();
}

// Later, right before Dispatch:
testingshader.SetVector("_CameraPosition", cam.transform.position);
testingshader.SetMatrix("_CameraToWorld", cam.cameraToWorldMatrix);
testingshader.SetMatrix("_CameraInverseProjection", cam.projectionMatrix.inverse);
testingshader.SetTexture(kernelIndex, "Result", renderTexture);
testingshader.Dispatch(kernelIndex, groupsX, groupsY, 1);

Notice the difference between SetVector and SetMatrix. Camera position is a vector, so it uses SetVector. Camera-to-world and inverse projection are Matrix4x4 values, so they must use SetMatrix. Passing a matrix into SetVector causes the CS1503 errors Unity showed in the Console.

Think of this like passing props into a React component. The compute shader cannot read your Unity scene hierarchy by itself. C# has to say: "Here is the camera position. Here is the camera rotation. Here is the output texture."

C# camera object
Lives on the CPU side. It knows the Unity transform, FOV, aspect ratio, and projection matrix.
Compute shader
Lives on the GPU side. It only knows values passed by SetVector, SetMatrix, SetTexture, and similar calls.
Dispatch
The moment C# says "run this kernel for this many groups of pixels."

Current project script: shadermanager.cs

This is the full version of Assets/basics/shadermanager.cs after the camera setup fix. Read it from top to bottom once: first Unity stores the shader/material references, then it caches the camera in OnEnable, then OnRenderImage sends camera data and dispatches the compute shader, then cleanup releases the render texture. 

using UnityEngine;

[ExecuteAlways]
[ImageEffectAllowedInSceneView]
[RequireComponent(typeof(Camera))]
public class shadermanager : MonoBehaviour
{
    [Header("Shader Settings")]
    public ComputeShader testingshader;
    public Material blendMaterial;

    [Header("Scene View")]
    public bool useShaderInSceneView = true;

    [Header("Blend")]
    [Range(0f, 1f)]
    public float blendStrength = 1f;

    private RenderTexture renderTexture;
    private int kernelIndex = -1;

    private Camera cam;

    void OnEnable()
    {
        cam = GetComponent<Camera>();
        RefreshKernel();
    }

    void OnValidate()
    {
        RefreshKernel();
    }

    void OnRenderImage(RenderTexture src, RenderTexture dst)
    {
        if (IsSceneViewCamera() && !useShaderInSceneView)
        {
            Graphics.Blit(src, dst);
            return;
        }

        RefreshKernel();

        if (testingshader == null || blendMaterial == null || kernelIndex < 0)
        {
            Graphics.Blit(src, dst);
            return;
        }

        EnsureTargetTexture(src.width, src.height);

        // The camera can be lost after script reloads in edit mode, so refresh it if needed.
        if (cam == null)
        {
            cam = GetComponent<Camera>();
        }

        testingshader.SetVector("_CameraPosition", cam.transform.position);
        testingshader.SetMatrix("_CameraToWorld", cam.cameraToWorldMatrix);
        testingshader.SetMatrix("_CameraInverseProjection", cam.projectionMatrix.inverse);

        testingshader.SetTexture(kernelIndex, "Result", renderTexture);

        int threadGroupsX = Mathf.CeilToInt(src.width / 8f);
        int threadGroupsY = Mathf.CeilToInt(src.height / 8f);
        testingshader.Dispatch(kernelIndex, threadGroupsX, threadGroupsY, 1);

        blendMaterial.SetTexture("_EffectTex", renderTexture);
        blendMaterial.SetFloat("_Blend", blendStrength);
        Graphics.Blit(src, dst, blendMaterial);
    }

    void RefreshKernel()
    {
        kernelIndex = -1;
        if (testingshader != null)
        {
            kernelIndex = testingshader.FindKernel("HelloWorld");
        }
    }

    bool IsSceneViewCamera()
    {
        return Camera.current != null && Camera.current.cameraType == CameraType.SceneView;
    }

    void EnsureTargetTexture(int width, int height)
    {
        if (renderTexture == null || renderTexture.width != width || renderTexture.height != height)
        {
            if (renderTexture != null)
            {
                renderTexture.Release();
                if (Application.isPlaying)
                {
                    Destroy(renderTexture);
                }
                else
                {
                    DestroyImmediate(renderTexture);
                }
            }

            renderTexture = new RenderTexture(width, height, 0, RenderTextureFormat.ARGB32)
            {
                enableRandomWrite = true
            };
            renderTexture.Create();
        }
    }

    void OnDestroy()
    {
        if (renderTexture != null)
        {
            renderTexture.Release();
            if (Application.isPlaying)
            {
                Destroy(renderTexture);
            }
            else
            {
                DestroyImmediate(renderTexture);
            }
            renderTexture = null;
        }
    }
}

Projection plane: why FOV changes ray directions

A pixel coordinate is flat. It is only "somewhere on the screen." To make a 3D ray, we pretend there is a rectangle floating in front of the camera. This rectangle is the projection plane. Each pixel maps to one point on that rectangle.

Same camera, different field of view

wide FOV: edge pixels spread outward narrow FOV: directions stay tighter

At a fixed distance from the camera, a wider FOV means the projection plane becomes taller and wider. The center pixel still points forward, but edge pixels are farther sideways on the plane, so their directions tilt outward more.

planeHeight = 2 * distance * tan(fieldOfView / 2)
planeWidth = planeHeight * aspectRatio

In world space, a point on the projection plane is built from the camera's own directions: 

Vector3 center = cameraPosition + cameraForward * projectionPlaneDistance;
Vector3 pointOnPlane = center
    + cameraRight * horizontalOffset
    + cameraUp * verticalOffset;

Vector3 rayDirection = (pointOnPlane - cameraPosition).normalized;

This is what RayDirectionVisualizer draws in Unity. Move the camera, rotate it, or change FOV, and the projection-plane points update because they are built from the camera transform and FOV.

The shader version of the same idea

The Scene View visualizer calculates projection-plane points in C# because it is meant for learning. The shader can do the same idea with matrices, which is more compact once you are comfortable. 

float2 uv = (id.xy + 0.5) / float2(width, height);
float2 clipXY = uv * 2.0 - 1.0;

float4 viewTarget = mul(_CameraInverseProjection, float4(clipXY, 1, 1));
viewTarget.xyz /= viewTarget.w;

float3 worldTarget = mul(_CameraToWorld, float4(viewTarget.xyz, 1)).xyz;
float3 rayOrigin = _CameraPosition;
float3 rayDirection = normalize(worldTarget - rayOrigin);

The matrix names sound intimidating, so translate them like this: inverse projection turns a screen point back into a point in camera space. Camera-to-world turns that camera-space point into world space. Subtract camera position from that point, normalize it, and now you have the ray direction.

A direction is not a ray. A ray is origin + direction * distance. The origin is the camera position. The direction is where this pixel is looking. The distance is how far along that line you want to test.

Where compute shaders fit

A compute shader is useful here because the work is naturally per-pixel. Pixel (0,0) can shoot its ray without waiting for pixel (1,0). The GPU is good at running thousands or millions of these tiny jobs in parallel. 

int kernel = rayTracingShader.FindKernel("Render");
rayTracingShader.SetVector("_CameraPosition", cam.transform.position);
rayTracingShader.SetMatrix("_CameraToWorld", cam.cameraToWorldMatrix);
rayTracingShader.SetMatrix("_CameraInverseProjection", cam.projectionMatrix.inverse);
rayTracingShader.SetTexture(kernel, "Result", target);

int groupsX = Mathf.CeilToInt(target.width / 8f);
int groupsY = Mathf.CeilToInt(target.height / 8f);
rayTracingShader.Dispatch(kernel, groupsX, groupsY, 1);
#pragma kernel Render

RWTexture2D<float4> Result;
float3 _CameraPosition;
float4x4 _CameraToWorld;
float4x4 _CameraInverseProjection;

[numthreads(8, 8, 1)]
void Render(uint3 id : SV_DispatchThreadID)
{
    uint width;
    uint height;
    Result.GetDimensions(width, height);

    if (id.x >= width || id.y >= height)
    {
        return;
    }

    // Create ray for this pixel here.
    Result[id.xy] = float4(0, 0, 0, 1);
}

Sphere hit: the question we are solving

A sphere is every point that sits exactly radius units away from its center. For a sphere centered at the origin, the equation is:

x*x + y*y + z*z = radius*radius

But our sphere does not need to be at the origin. If the sphere center is sphereCenter, then the vector from the center to any test point is:

testPoint - sphereCenter

If that vector's squared length equals radius * radius, the test point is on the sphere surface.

A ray gives us many possible test points:

pointOnRay = rayOrigin + rayDirection * distance

So the real question is: "Is there any distance value where the point on the ray lands on the sphere surface?"

How do we know the number of intersections?

When you substitute the ray equation into the sphere equation, the unknown is distance. The result is a quadratic equation. A quadratic can have zero, one, or two real answers.

Three possible ray-sphere outcomes

miss: 0 intersections tangent: 1 intersection hit through sphere: 2 intersections

The discriminant is the part under the square root:

discriminant = b*b - 4*a*c
discriminant < 0
No real square root. The ray misses the sphere. There are 0 intersections.
discriminant == 0
One answer. The ray just touches the sphere. This is a tangent hit.
discriminant > 0
Two answers. The ray enters the sphere at one point and exits at another.

In rendering, we usually want the nearest visible hit, so when there are two answers we choose the smaller positive distance. The bigger distance is the exit point on the far side of the sphere.

HitSphere line by line

Here is a beginner-friendly version of the function. Read it as: move the sphere problem to the origin, solve the quadratic, reject misses, choose the nearest positive hit. 

bool HitSphere(
    float3 rayOrigin,
    float3 rayDirection,
    float3 sphereCenter,
    float sphereRadius,
    out float hitDistance
)
{
    float3 offsetRayOrigin = rayOrigin - sphereCenter;

    float a = dot(rayDirection, rayDirection);
    float b = 2.0 * dot(offsetRayOrigin, rayDirection);
    float c = dot(offsetRayOrigin, offsetRayOrigin) - sphereRadius * sphereRadius;

    float discriminant = b * b - 4.0 * a * c;

    if (discriminant < 0)
    {
        hitDistance = 0;
        return false;
    }

    float closestDistance = (-b - sqrt(discriminant)) / (2.0 * a);
    float farDistance = (-b + sqrt(discriminant)) / (2.0 * a);

    hitDistance = closestDistance;

    if (hitDistance < 0)
    {
        hitDistance = farDistance;
    }

    return hitDistance > 0;
}

Why subtract sphereCenter?

A sphere equation is easiest when the sphere is centered at zero. Instead of moving the sphere to zero, we move the ray into the sphere's local point of view: 

float3 offsetRayOrigin = rayOrigin - sphereCenter;

This means "where is the ray origin relative to the center of the sphere?" Sebastian says this quickly as conceptually keeping the sphere at zero and moving the ray instead.

What are a, b, and c?

They are the quadratic coefficients. You do not have to memorize the derivation at first. What matters is that they come from plugging the ray formula into the sphere formula. 

ray point:      rayOrigin + rayDirection * distance
sphere test:    length(point - sphereCenter)^2 = radius^2
result shape:   a*distance^2 + b*distance + c = 0

Why return only one hit distance?

The function can detect whether the math has zero, one, or two intersections, but the renderer usually only needs the closest visible surface. A pixel can only show the first thing the camera ray sees.

Open SphereIntersectionVisualizer in Unity. Aim the ray through the sphere. The first contact point is what the shader needs for color, normal, lighting, and bouncing.

After the hit: position and normal

Once we know hitDistance, we can recover the actual world-space hit position: 

float3 hitPoint = rayOrigin + rayDirection * hitDistance;

The normal is the direction from the sphere center to the hit point. This tells us which way the surface faces. 

float3 normal = normalize(hitPoint - sphereCenter);
float3 debugColor = normal * 0.5 + 0.5;

This normal-to-color trick is why you often see spheres shaded like rainbow direction maps. Red means the surface normal points more along world X. Green means world Y. Blue means world Z.

Coordinate sky: direction as color

Before lighting, Sebastian outputs ray direction as color to check that the camera math works. This is a debugging skybox. It answers: "Are my world-space directions correct?" 

float3 CoordinateSky(float3 rayDirection)
{
    return rayDirection * 0.5 + 0.5;
}

Look toward positive X and the view becomes more red. Look upward and it becomes more green. Look forward and it becomes more blue, depending on your world orientation. If you look into directions where X, Y, and Z are all negative, the remapped color gets dark.

Multiple objects: closest hit wins

After one sphere works, Sebastian moves to multiple spheres. The idea is simple: ask every object whether it was hit, keep whichever hit has the smallest positive distance. 

float closestDistance = 1000000.0;
bool didHitAnything = false;

for (int i = 0; i < sphereCount; i++)
{
    float distance;
    if (HitSphere(ray.origin, ray.direction, spheres[i].position, spheres[i].radius, distance))
    {
        if (distance < closestDistance)
        {
            closestDistance = distance;
            didHitAnything = true;
        }
    }
}

This is the ray tracer's version of depth. In Unity's normal renderer, the depth buffer handles nearby things covering far things. In our ray tracer, closest positive hit distance handles that.

Planes: the second basic shape

A plane is an infinite flat surface. It has a point and a normal. The point anchors it in the world. The normal says which way it faces. 

bool HitPlane(float3 rayOrigin, float3 rayDirection, float3 planePoint, float3 planeNormal, out float hitDistance)
{
    float denom = dot(rayDirection, planeNormal);

    if (abs(denom) < 0.0001)
    {
        hitDistance = 0;
        return false;
    }

    hitDistance = dot(planePoint - rayOrigin, planeNormal) / denom;
    return hitDistance > 0;
}

The dot product tells us whether the ray is heading into the plane or sliding almost parallel to it. Use PlaneIntersectionVisualizer to see this: when the ray is parallel, no matter how long it travels, it will not cleanly meet the plane.

Why Unity meshes do not automatically count

A compute shader does not automatically know about the objects in the Hierarchy. If you create a Unity sphere mesh, the compute shader cannot collide with it unless C# sends shape data to the shader.

For now, treat Unity objects as authoring handles:

  • Sphere transform position becomes sphereCenter.
  • Sphere transform scale becomes sphereRadius.
  • Plane transform position becomes planePoint.
  • Plane transform up direction becomes planeNormal.

Real arbitrary meshes come later. They require sending triangle data to the GPU in a StructuredBuffer and doing ray-triangle intersections. Spheres and planes are the right first step because they teach the core ray logic without triangle bookkeeping.

Materials and light

Once hits work, we attach meaning to surfaces. Sebastian introduces material data: color, emission color, and emission strength. 

struct RayTracingMaterial
{
    float3 color;
    float3 emissionColor;
    float emissionStrength;
};

A red material does not create red light. It filters light, keeping red and absorbing more green/blue. An emissive material creates light. 

float3 rayColor = float3(1, 1, 1);
float3 incomingLight = float3(0, 0, 0);

incomingLight += material.emissionColor * material.emissionStrength * rayColor;
rayColor *= material.color;

Diffuse bounces

A rough object scatters incoming light. A simple path tracer picks a random direction in the hemisphere above the surface normal. 

float3 RandomHemisphereDirection(float3 normal, inout uint seed)
{
    float3 direction = RandomUnitVector(seed);

    if (dot(direction, normal) < 0)
    {
        direction = -direction;
    }

    return direction;
}

HemisphereBounceVisualizer shows this in Scene View. The normal is the "up" direction of the surface, and every bounce direction is forced to stay above that surface.

The trace loop

Now the final Sebastian-style structure makes sense. One ray starts at the camera. It hits something, gathers emission, gets tinted by material color, bounces, and repeats. 

float3 Trace(Ray ray, uint seed)
{
    float3 rayColor = float3(1, 1, 1);
    float3 incomingLight = float3(0, 0, 0);

    for (int bounce = 0; bounce < MaxBounceCount; bounce++)
    {
        HitInfo hit = CalculateClosestHit(ray);

        if (!hit.didHit)
        {
            incomingLight += CoordinateSky(ray.direction) * rayColor;
            break;
        }

        incomingLight += hit.material.emissionColor * hit.material.emissionStrength * rayColor;
        rayColor *= hit.material.color;

        ray.origin = hit.position + hit.normal * 0.001;
        ray.direction = RandomHemisphereDirection(hit.normal, seed);
    }

    return incomingLight;
}

The little offset along the normal prevents the next ray from instantly colliding with the same surface because of floating-point precision.

Turn on PathTraceStepVisualizer. It draws a single version of this loop. The compute shader performs the same story per pixel.

Why path tracing gets noisy

Random bounces mean random answers. One sample per pixel is noisy because each pixel only asks one random question. Accumulation asks many random questions over time and averages the answers. 

float3 oldColor = PreviousFrame[pixel];
float3 newColor = Trace(ray, seed);
float3 average = lerp(oldColor, newColor, 1.0 / frameIndex);

When the camera moves, the old answers describe an old view, so accumulation should reset. That is why path traced previews often clear and become noisy again after camera movement.

Your learning plan

Work through it like Sebastian does: make the invisible visible before making it fast.

  1. Use RayDirectionVisualizer until projection plane and FOV feel real.
  2. Output ray direction as color in the shader.
  3. Use SphereIntersectionVisualizer until the discriminant makes sense.
  4. Render one sphere as black/white hit/miss.
  5. Render normal color from the hit point.
  6. Add multiple spheres and closest-hit logic.
  7. Add planes.
  8. Add materials, emission, and random bounces.
  9. Add accumulation after the image is noisy but correct.
